# Tune Garden — Long-Term Editor Design (v2)

*Companion to `DESIGN.md` (vision), `PACKAGES.md` (content DAG), and `SAVE-SHARE.md` (song format). This document is the source of truth for how the **editing surface and its underlying document model** evolve as the remaining systems land (meter, duration, dynamics, multi-voice, sections, chromatic).*

*v1 drafted 2026-07-16 (owner + Claude). **v2 2026-07-19**: revised after expert review (`Feedback 2026-07-19.docx`) and owner decisions — see §18 for the changelog. Verdict adopted from the review: proceed with the v1 architecture, but make the **foundation more musically general than the initial UI**.*

**Status: DESIGN — nothing here is built yet.** Build phases in §16; each ships value on its own.

---

## 0. Why now

Every remaining package wave is gated on an editor capability (meter → `two-kinds-of-walking`; duration → R3/Region 7; dynamics → `rain-and-sun`; multi-voice → Region 6; sections → Region 7; chromatic → Wave D). Designing the editor once, now, means each of those lands as a planned part of one architecture instead of repeated rebuilds.

## 1. The ceiling (product destination) — DECIDED 2026-07-19

**Tune Garden becomes a serious musical composition and arrangement environment — not a DAW, and not a notation application.** Notation is an educational/export *lens*; detailed audio production happens in external tools.

In scope long-term: multi-part compositions, real form (sections/repeats/variation), dynamics and (later) articulation, changing keys and meters eventually, **MIDI export** (early), **rendered audio export**, **MusicXML export later** (only if/when notation semantics mature), MIDI keyboard *input* eventually, remix and collaboration.

Explicitly out of scope: audio recording, waveform editing, plug-ins/effects racks, automation lanes, mixing/mastering beyond the simple per-voice mixer. If a feature request looks like GarageBand/Ableton/MuseScore, the answer is an *export*, not a feature.

## 2. Principles (non-negotiable)

1. **It stays a garden.** Seeds, plots, blooms, tools, creatures. Every new power arrives as a metaphor; can't-sound-bad remains the *default* experience; danger is opt-in and earned.
2. **One engine and document model everywhere; workspaces adapt.** Levels, Studio, phone, and desktop share semantics, undo, playback, and persistence — but not necessarily identical controls or chrome. A level shows seeds and one new tool; an advanced Studio may show an inspector and shortcuts. There is no second engine.
3. **Notes are objects; every visible surface is a lens.** The model is a list of musical objects (§4); the field, the future score view, and the legacy grid are projections. Lenses control presentation — they never constrain what a song can represent.
4. **The model is chromatic and tick-based; friendly views never reduce musical precision.** Columns, vines, and lighting are views over exact musical data (12-semitone pitch, integer-tick time, continuous velocity).
5. **Names and numbers are never required — and never forbidden.** The beginner experience runs entirely on HOME, sun/moon, colors, and feel. Optional labels (note names, "C major", measure numbers, precise values) are available for those who want them — the same tiering philosophy as the dimmed teach-field.
6. **Touch-complete, keyboard-accessible, desktop-efficient.** Every operation is possible on touch; desktop adds keyboard navigation, shortcuts, marquee selection, and (eventually) computer-keyboard/MIDI note entry. No essential feature hides behind hover or an undiscoverable gesture.
7. **Every action is reversible and recoverable.** Undo/redo, frequent local autosave, crash recovery, and named checkpoints are core design rules, not features.
8. **Never break shipped content.** All packages' goal detectors, the FAMOUS library, saved songs, and share links keep working at every phase (§15).

## 4. The document model (the heart of v2)

### 4a. Shape

```
project        { version, ppq, tempoMap, meterMap, tonalityMap, tracks[], sections[], arrangement[] }
track          { id, role, instrument, mixer }            // role: melody | support | drums | …
note           { id, pitch, startTick, durationTicks, velocity, spelling?, articulation? }
section        { id, name, lengthTicks, eventsByTrack }
arrangementItem{ id, sectionId, repeats, transpose? }
```

Optional fields (`spelling`, `articulation`, `transpose`) are **reserved seams**, not near-term work.

### 4b. Time is ticks, not columns

Canonical time is integer **ticks at PPQ = 96** — **RATIFIED by the 2026-07-19 spike** (`spike/FINDINGS.md` §1): smallest supported subdivision = 32nd note and 16th-triplet; quintuplets/septuplets out of scope per §1; MIDI export multiplies by 5 losslessly if 480 PPQ is wanted. (96 is divisible by 2/3/4/6/8/12/16/24/32 — 16ths, triplets, and finer are representable without floats.) Columns are a *grid projection at the current snap resolution*. Today's column = an 8th = 48 ticks; v3 songs convert exactly (`start = col·48`, `len = len·48`). This makes triplets, pickups/anacrusis, ties across bars, swing-as-view, snap changes, zoom, and future meter changes representable **without another migration** — none of them need UI yet.

### 4c. Stable IDs, from Phase 0

Notes, tracks, sections, arrangement items, and saved tools all carry IDs. Needed for reliable selection, undo, overlapping notes, section references, cloud revisions, remix provenance, and any future collaboration. Cheap at the model flip; brutal to retrofit.

### 4d. Three kinds of state, kept separate

- **Music document** — notes, tracks, sections, meter/tempo/tonality maps. The only thing saved in a song.
- **Editor/session state** — selection, active tool, lens, zoom, scroll, open section, Composer-mode flag. Never serialized into songs.
- **Derived projections** — the legacy boolean grid, visible cells, detector inputs. Recomputed, never stored.

### 4e. Pitch is musical (written) pitch

`note.pitch` is the musical pitch; **instrument playback transposition is a track/instrument property** (the glockenspiel's existing `up:24` is this concept — it graduates from playback hack to model field). Velocity is continuous internally (0–1); kid-facing UI exposes 4–5 named levels.

### 4f. Tonality is a map, not a constant

One HOME+mode per song initially, but the model reserves `tonalityMap` (per-section or per-range lighting) so modulation, key changes between sections, and borrowed-color contexts don't require a rebuild. No UI until a package needs it.

## 5. The pitch system: lattice + lighting

### 5a. The lattice

A **12-semitone-per-octave lattice**: 7 **wide** lit rows (the palette — full-height plots, guaranteed-good, carrying the layout like piano white keys) + 5 **slim** "crack" rows (unlit, darker, locked until the chromatic milestone, where planting one = *borrowed color magic*). Two octaves ≈ today's field height. B–C and E–F visibly touch (no crack) — semitone geography readable at a glance (fixes the Soft Wobble visual TODO structurally).

**✅ Gate closed (2026-07-19, two-round phone test — `spike/FINDINGS.md` §5):** the lattice ships **strategy A — compressed slim rows with an invisible ±5 px crack hit band** beyond each crack's visual edges (slim effective touch band 22 px; a wide row between two cracks keeps 24 of its 34 px). Owner-measured target practice: **wide 99% / slim 93%**; ±7 px flipped the trade the wrong way (92/97 — wide rows carry most planting), and ±9 over-served cracks (91/100). Benched alternatives: black-key chips (98/90, passed but visually busier — the fallback if real play disagrees); tap-opens-the-crack (never ambiguous — retained as the candidate *pre-unlock* "not yet" gesture); zoom-to-plant. The compressed-row look ships clean: nothing visible changes at the cracks.

### 5b. Lighting = tonality; names optional

- **HOME** (R17): a draggable marker on the row gutter (green rows follow). **MODE**: a separate major/minor switch (sun/moon), extending later to modal lighting patterns (`mist-paths`).
- Lighting is derived: `lit = pattern(mode) rotated to home`. Discoverables: home slid by a fifth changes exactly one lit row (the circle of fifths made physical); major↔relative minor changes only the green rows; major→minor *on the same home* changes several lit rows — a different, equally teachable move.
- Optional labels (per §2.5): row names, a "C major" readout, measure numbers — off by default, available in Studio/Composer mode.

### 5c. Distinct operations (each a future teaching mechanic — never conflated)

| Operation | What moves | What it means |
|---|---|---|
| Drag HOME (notes fixed) | lighting only | *reinterpretation* — same notes, new gravity |
| Drag notes (lighting fixed) | notes only | transposition **against** the key — relationships change |
| Drag both together | notes + lighting | conventional whole-piece transposition — same music, new height |
| Move by rows (lit) vs by semitones | — | scale-degree motion vs exact motion — different tools |

### 5d. Saved tools declare their transposition nature

A stamp is one of: **exact interval shape** (chromatic — keeps quality everywhere), **scale-degree pattern** (adapts to the lighting — a triad stamped on different degrees changes quality, correctly), or **literal pitch fragment**. Both stamping modes are musically valuable; the lattice makes both cleanly implementable. (Supersedes v1's claim that the DESIGN §11 fork "resolves" — it *separates*, which is better.) *Spike addendum:* the gesture prototype confirmed this empirically — a literal-pitch stamp anchored off its home position on a diatonic field silently drops out-of-palette notes, so **the default stamp mode on the garden lens is scale-degree**, with exact/literal as declared alternatives.

### 5e. Lenses and vertical scroll

| Lens | Shows | Who/when |
|---|---|---|
| **Garden** | Only lit rows — today's fields pixel-for-pixel; chromatic notes render as "visitor" seeds pinned between rows (inspectable/editable via tap → their crack breathes open) | all current levels, beginners |
| **Lattice** | wide + slim rows | Studio; post-chromatic levels |
| **Piano roll** | 12 equal rows, pinch-zoom, exact distances | the lab; Soft Wobble revisit; Secret Doors |

The pitch window pans vertically (R16): default ~2 octaves centered on home (range grows toward C3–C7; tune by ear), overview ribbon marks home + off-screen seeds; levels pin the window, Studio frees it.

## 6. The time system

- **Meter & bars (R2):** per-song time signature as a *dance feel* (march 4s · waltz 3s · lopsided later). Bar fence-posts; the beat guide derives from meter. **Snap resolution is independent of meter** (8ths default; 16ths/triplet snap unlockable). Pickups and ties across bars are representable (ticks) before they are teachable.
- **Duration (R6):** drag a seed rightward → it grows a **vine**. A vine means "*hold for this musical duration*" — each instrument realizes it honestly: pads sustain, piano decays undamped, kalimba rings its natural length; **no artificial loop-sustain** unless it genuinely sounds good. Score duration stays independent of acoustic decay.
- **Playback (R12):** play-from-playhead/selection, loop range, count-in + metronome (quiet, optional).
- **Navigation (R8):** column zoom + minimap strip for songs > 2 bars, growing into the section strip.

## 7. Dynamics (R3)

Tools: **sunlight / shade** (louder/softer) — *not* pruning shears (pruning reads as shortening; that's the vine's word). Tap or drag across notes; louder = bigger, more saturated bloom. 4–5 kid-facing levels over a continuous internal velocity; later, paint a crescendo across a selection in one gesture. Drum-pad accents come later (R4-tier rhythm), same model.

## 8. Multi-voice (R5)

Tracks exist in the **model from Phase 0** (today's melody/drums become two tracks); the *UI* ships in Phase 4: translucent layers over one field (active voice full-color, others ~35% ghost), voice chips to switch, per-voice instrument + mute/solo + velocity. Garden framing: voices are creatures/species (roots bass, canopy birds — `deep-roots-high-birds`). Start at 2 voices, cap ~4.

## 9. Sections & form (R9)

- A piece = **section definitions** + an **arrangement list of instances** (never physical copies). Three distinct actions, visible in the path strip: **repeat** (same section referenced again — editing updates all occurrences), **duplicate** (explicit independent copy), **variation** (duplicate, then diverge; a shared-motif reference model can come later if divergence chores hurt).
- The **path strip**: tiles (🌸 A · 🌙 B · 🌸 A) reordered, repeated, cloned. "The path loops back through the meadow." A′ is a duplicate with a tick — the strip labels it A′ automatically.
- Sections may later carry their own meter/tempo/tonality (the maps in §4 make this a data question, not a rebuild).

## 10. Editing, tools, and the gesture grammar

- **Transactions:** every mutation is a semantic operation (place/remove/move/resize/paint/paste/section ops) in a command journal → undo/redo (~100 deep), and later the journal is the seam for cloud revisions (not a CRDT — see §14).
- **Seed tray (R10):** select region → seeds lift into a tray → move / copy / delete / drag-transpose / **save to toolbox as a stamp** (declaring its §5d nature). The toolbox remains the scalability engine (Tiny Motifs' lesson as a power tool).
- **Time surgery:** insert/remove musical time (bar-aware), replacing "redo everything after the mistake."
- **Gesture grammar:** the **input-state table** is written and prototyped (`spike/FINDINGS.md` §2, `spike/gestures.html`): tap empty = plant · tap note = select + handles (tap again = deselect) · drag body = move (whole selection if selected) · drag end handle = resize (vine) · long-press empty (350 ms, 8 px slop) = marquee selection · **drag empty or two-finger = pan** (the spike showed one-finger pan on empty coexists cleanly with tap-plant and long-press-marquee — both pan forms ship). Thresholds (350 ms / 8 px) to be confirmed in the owner's phone test. *Phone-test addendum (2026-07-19):* **any armed/pending mode (stamp placement, and future tools that capture taps) must still route drags to pan**, with the pending action surviving the pan and re-arming on release — the owner hit exactly this dead-end in round 1; and the minimap/section strip is a **scrub control**, never a readout.
- **Desktop baseline (Phase 1):** arrow-key navigation, visible focus, shortcuts for undo/copy/paste/play, marquee select.
- **Inspector (Composer mode only):** a compact panel for the selection — start, duration, pitch/name, velocity, track. Numbers optional, never required.

## 11. Workspaces & capability gating — DECIDED 2026-07-19

- **Levels:** declare lens, pitch window, meter, tools, voice count (the generalization of `unlock`/`palette`/flags). All shipped levels = today's configuration.
- **Studio:** capabilities unlock **by progression** (the hidden-curriculum identity — powers are earned).
- **Composer mode:** an **off-by-default switch in settings** (per account) that unlocks *Studio tooling only* — inspector, all lenses, full range, keyboard entry, optional labels — for players who already know theory and want Tune Garden for composing. It never unlocks level content, famous reveals, or region progression: it opts out of *pacing*, not of the game.
- **Phone portrait = light mode:** listen, tweak, small edits. **Full authoring = landscape/desktop.** The Phase-1 gesture work targets this split explicitly.

## 12. Audio engine & performance (R18, R21)

- **Scheduler:** lookahead scheduling against `AudioContext.currentTime` (browser timers *wake* the scheduler; they never set sound time). Note-on **and note-off** (duration), cancellation/rescheduling on live edits, seek, deterministic loop boundaries, per-track buses feeding the existing mixer. Lands with Phase 0 as an abstraction; fully exercised by Phase 2 (duration) and 4 (voices). **Spike-validated 2026-07-19** (`spike/FINDINGS.md` §3): 10,000 notes at 200 BPM with live edits and forced 30 ms main-thread stalls → zero late notes, p99 wake lateness 3.2 ms, ~4× headroom under a 120 ms lookahead.
- **Background-tab throttling (spike discovery):** browsers throttle timers in hidden tabs to ≥1 s unless the tab is audibly playing; the starvation case is *muted playback in a background tab*. The scheduler must stretch lookahead/wake (~1.5 s / 250 ms) on `visibilitychange` and shrink back on return.
- **Budgets (set by the spike 2026-07-19, enforced after; details in `spike/FINDINGS.md` §4):** target device = ~4-year-old mid-range Android · visible cells ≤ ~1,800 (beyond that, window via R8/R16 paging and pitch scroll, don't grow the DOM) · full grid rebuild ≤ 100 ms on target, incremental restyle ≤ 16 ms · edit latency ≤ 50 ms, plant-to-sound ≤ 60 ms · ≤ 1,000 notes/section, ≤ 8,000 notes/song, ≤ 4 pitched tracks + drums · scheduler alarm if wake-lateness p99 > 80 ms · sample memory ≤ today ×2 until measured on target. Rendering stays DOM but **viewport-based**, so virtualization (or canvas) remains possible without a rewrite.

## 13. Accessibility (R20 — new in v2)

Complete keyboard operation; visible focus and sane focus order; screen-reader names for notes ("C5, bar 2, beat 3, loud") and controls; reduced-motion support; non-color indicators for lit/unlit/home/velocity (shape/size/texture already do much of this); high-contrast support; tap-hold twins for every hover affordance; narration (Polly) never colliding with editor feedback.

## 14. Persistence & sharing — DECIDED 2026-07-19

- **Local:** frequent autosave, crash/session recovery, named checkpoints ("versions" a child can understand and restore).
- **Cloud:** revision numbers per song; last-writer-wins with a revision check (two devices editing = second gets a gentle "newer version exists" fork prompt).
- **Sharing = snapshot + remix-with-ancestry.** A shared link opens an immutable snapshot; "remix" creates a copy carrying provenance (author chain). **Live co-editing is explicitly deferred** — the founding co-op vision stays on the map, and stable IDs + the transaction journal are the seams that make it feasible later, possibly as one of several modes. No CRDT now.

## 15. Compatibility & migration (R13, R15)

- **Detector strategy:** shipped detectors keep reading the projected `grid[r][c]` (recomputed on mutation) — but the projection is a **temporary adapter, not the permanent interface**. A small musical query API grows beside it: `notesStartingAt(t)`, `notesSoundingAt(t)`, `pitchesAt(t, track?)`, `onsetGrid({resolution, track})`, `notesInRange(r)`. New detector families (duration, dynamics, voices, sections) are built on queries from day one; old ones migrate opportunistically.
- **Save v4** = ticks (`ppq`), IDs, tracks, sections + arrangement, velocity, meter/tempo/tonality maps. v3 loads forever (up-convert: one section, one melody + one drum track, col·48 ticks, default velocity, 4/4). The packed wire format gains optional tail fields; old `#s=` links never break.
- **FAMOUS library:** unchanged short-term; real duration eventually ends the "re-strike ties" workaround (entries can then carry honest `len`).

**THE CLAIM TEST IS DIRECTION, NOT SPREAD-VERSUS-TRAVEL, and that cost a device round to learn.** The first build compared how far the fingers spread against how far their midpoint travelled. **THE LISTENER MUST BE BORN WITH THE SECOND FINGER, and the instrument built to settle this gave the wrong answer.** `spike/pinch-probe.html` A/Bs a blocking `touchmove` registered at load against one registered mid-sequence; on the Pixel its box read lazy=*not cancelable*, at-load=*cancelable*, so the build was changed to register at load — and **both pinch and two-finger pan stopped working entirely.** Mechanism: present from the first finger down, Chrome asks the main thread on the very first move, one finger is a scroll so we decline to prevent, Chrome commits to scrolling, and every later move of that sequence is already spoken for. **DECIDED — WHAT A COLUMN IS WORTH, AND HOW BARS WORK (owner, 2026-08-27; two rounds of adversarial review, both returning "replace" before this survived).** This is the decision Phase 2's meter/bars/dance-feels/`beatcol`/bar-numbers/loop-range/count-in work was blocked on. It began as "is a bar 8 columns or 16?" — the doc model says a column is an eighth (`TICKS_PER_COL=48` against `TG_PPQ=96`), while every rhythm detector and every line of user copy is built on beat = 4 columns. **The owner's own question dissolved that framing:** *"if we have 8 or 16, how are we going to implement time signatures such as 3/4 or 6/8?"* A fixed columns-per-bar cannot express them, and — the part a single number can never carry — **3/4 and 6/8 are the same LENGTH and differ only in grouping**, so a meter is two facts, not one.

**THE DECISION.** (1) **Ticks are canonical; a column is a projection.** "What a column is worth" was never a fact about the music — it is a fact about the editor's grid. (2) **Snap is view/session state and NEVER a timebase.** It may not touch `stepDur`, and it is not stored as musical semantics. (3) **Meter lives in `doc.meterMap`** — the reserved §4f seam, not a scalar `time.meter` that bypasses it — as `{tick, preset, originTick}`, a list with exactly one tick-0 event enforced in the UI for now, so mid-song meter changes (out of scope by owner's call) are not nailed shut. (4) **`originTick` is mandatory.** Moldau's downbeat is at column 1; Amazing Grace and Taps open with pickups; without an origin, barlines are wrong even when the signature is right. (5) **Presets carry numerator, denominator, an AUTHORED beat grouping, and the displayed/count-in pulse unit** — grouping must never be derived, because derivation cannot separate 3/4 from 6/8 and fails outright on 5/8, 7/8 and hemiola; and a jig's felt pulse is a dotted quarter, so "80 BPM" needs the preset to say what a beat *is*. (6) **Meter never controls timeline length** — a song may end mid-bar and many do (famous entries run 46, 52, 66, 98 columns). Meter may *offer* Add Bar; it may never normalise, pad or round `COLS`. (7) **Levels never show a time signature** — the child picks a dance feel (march/waltz/jig) and the meter follows; **the Studio exposes it directly.**

**WHAT TWO ROUNDS OF REVIEW KILLED, kept because the reasoning is the load-bearing part.** *Round 1* destroyed the first draft's central claim that a column is universally an eighth. An audit of all 18 `FAMOUS` entries **from note positions rather than comments** found both conventions in frozen content, and destroyed the sentence the whole draft rested on — *"none of this is audible-wrong today; it is named wrong"* — with nine citations: drum pads tint every 4th column `beat`, `beatGuide` glows every 4th melody column, Hi-hat Shimmer's copy says *"eight times across the bar"*, Wind and Gaps counts *"the first bar (16 steps)"*, the ＋ tooltip says *"one more bar (16 steps)"*, Off the Path physically slides columns 2,6,10,14. One beat = 4 columns.` against `const MAX_VINE=8; // a whole note` — eight columns is a whole note only if a beat is two). **The recorded lesson from the widthBand round repeated itself exactly: comments and labels are weaker evidence than behaviour, and the draft was built out of comments.** *Round 2* killed the rewrite's new mechanism — a snap-derived `stepDur` with "declare a level 16th-snap and halve its tempo" — on two grounds. Conceptually it ran the projection contract backwards: it declared ticks canonical and columns the projection, then held **columns** fixed and moved the **ticks**, which is a content rescaling. Operationally it was worse than risky, and this was verified in source rather than argued: **there are no per-level tempo numbers to halve.** Tempo is a single global player setting (`progress.settings`); the slider is `min="60"` while the required values are 39/41/50/52/58; and `applyGrooveTempo()` slams `tempoEl.value = GROOVES[i].bpm` anyway, with `runReveal({jam:true})` firing it during scripted reveals without the player touching anything. **§5(a) had no mechanism at all.** Removing snap from the transport dissolved that finding and three others with it — the fix was a subtraction, not more design.

**§5 — THE FOUR-COLUMN BEAT, THE PART THAT DOES NOT DISSOLVE, AND IS DELIBERATELY LEFT OPEN.** With snap as view state, the shipped rhythm levels **cannot be made true by relabelling**: their kick genuinely sits on beats 1 and 3. So this is a labelling question with two self-consistent answers and **no sound change either way** — either the tempo box is honest and the "beat" copy is wrong, or the beat copy is honest and the box reads double. The evidence splits the packages, and the split is the answer: **`swingTicks` carries both conventions in adjacent lines.** `if(jamMode && col%2===1)` pushes odd columns by a swing fraction — coherent only at EIGHTHS. `if(levelSwing && col%4===2) return TICKS_PER_COL` delays columns 2,6,10,14 by a whole column — coherent only at 16THS, where those are the "&"s and the delay is a shuffle; under the eighth reading they are downbeats and it drags a backbeat half a beat late. That is the strongest *behavioural* evidence in the file that the feel levels were authored on a 16th grid. Therefore: **the three `beatGuide`-only packages get their WORDS fixed, not their grids** (zero code risk, no migration, no format churn — "bar (16 steps)" becomes two bars, and the tint gets an honest name), while **the `feel:true` packages are genuinely unresolved and become their own scheduled job**, because `levelSwing` cannot be fixed with words. Pretending otherwise is how the first two drafts went wrong.

**FAMOUS ENTRIES.** Meter is **hand-entered from the scores, never inferred** — an analyser can rank candidates by downbeat/onset coincidence but cannot separate 3/4 from 6/8 and cannot find a pickup; use a scorer only as a *post-entry lint* that flags disagreement with what was typed. Eighteen entries (not seventeen — that is the count of *earlier* ones) is small enough that hand-entry is cheaper and more trustworthy. **The legacy no-bars quarantine is over-applied if it covers the Jukebox:** standalone Jukebox/Studio famous songs have no level to collide with and may carry explicit meter and origin once their timing unit is hand-validated. **Capstone rewards stay bar-less**, because `placeFamous` wipes the field, widens `COLS`, overwrites the tempo, and leaves the arrangement on the grid for ▶ — so a reward carrying its own meter creates a three-way authority collision (it inherits the level's meter and draws false bars, or overwrites it and makes the child's chosen dance feel stale, or the UI shows two authorities). Chopsticks is already 3/4 and Moldau already 6/8, so this is live. **Note lengths stay the separate batched pass** the owner already scheduled; the first draft proposed merging them and contradicted a standing rule in `DESIGN.md`.

**TRAPS FOR WHOEVER BUILDS THIS.** `packSong` returns a **positional** array `[3, palette, cols, tempo, groove, voice, notes, hits]` against `SHARE_MAX=1800` — meter/snap may only ever be **appended as slot 8**, never inserted, and must be genuinely OMITTED rather than assigned `undefined`, which JSON serializes as `null` and breaks byte-identity. `unpackSong` must read absence as **unmetered** — decoding it as an explicit 4/4 would give every old share link visible bars, contradicting the quarantine. `snapState` snapshots `{palette, cols, tempo, groove, tracks}`; meter must join it or undo silently fails to restore a meter change. `resetTransient` wipes tracks but does not recreate the doc or clear its maps, so a metered package would leak into the next legacy level. **Changing snap on a song that already has content is destructive, not merely re-drawn:** `noteCol()` rounds `startTick/TICKS_PER_COL` and both `reproject()` and `currentSong()` filter `c >= COLS`, so halving snap doubles every column index and silently drops everything past the end — a live Studio snap control must scale `COLS` with it. **Dance feels are not free:** `jamStep` wraps `%16` and picks chords by `s/4`, structurally fixed to a 16-column four-step cycle, so a 3/4 or 6/8 song keeps a backing band crossing every barline — waltz and jig need new groove content, and meter alone cannot deliver PW-5's "march, sway, spin". The `TICKS_PER_COL` audit (44 references) is the easy half; the hard half is the unwritten column assumptions — `%4` beat tint, swing placement, `LEN_BEATS=[0,4,8,12]`, camera landing rungs, the 16-column patch control, the reveal pulse — where a blind mechanical replacement breaks shipped goals and leaving them hardcoded breaks new meters. **Goldens are blind to exactly this class of change** (five step schedules; no famous playback, held notes, pickups, loop boundaries, count-in or non-4/4 grooves): a snap change can leave every recorded wall-clock step identical while turning two bars into one. New goldens come first, not after.

**FIRST SLICE:** not format-only barlines. One end-to-end **Studio** slice — explicit meter + origin, rendered bars and beats, meter-aware Add Bar, undo/save/share, and a bar loop range (which `loopStart` is already waiting for) — or ship it with the first package that uses it. Count-in and dance grooves may be deferred; bars must *do* something.

**✅ BUILT 2026-08-28 — THE FIRST SLICE, exactly as scoped above, in two PRs (goldens, then the feature atomically).** `METERS` carries four presets with AUTHORED `beats[]` and a `pulse`; `doc.meterMap` holds at most one `{tick:0, preset, originTick}`; and **one pure function, `meterLayout(cols, m)`, is the single source of truth** for the strip's chips, both barline overlays and the drum pads' tint — pure precisely because **no golden can see a barline**, so unit tests over it are the only place bar positions are ever checked at all. Verified in the browser for all four presets × pickups 0–2: 4/4 draws bars at 0/8 and beats at 2/4/6/10/12/14; **3/4 and 6/8 draw identical barlines (0/6/12) and completely different beats (2,4,8,10,14 against 3,9,15)**, which is the two-facts claim made visible; a 16-column waltz's third chip is clipped to 4 columns; and a 2-column pickup is bar 0, unnumbered, with bar 1 at the origin and the pickup's own beat drawn at column 0.

**THE BARS LIVE ON `#cursorStrip`, AND THE FIRST DESIGN PUT THEM SOMEWHERE ELSE.** A new `#barRuler` inside `.scroller` was argued for on the grounds that it had "no existing pointer contract" — exactly backwards, and the review said so: the stake's rail has an *explicit* contract with four exclusion sites already written for it, while a new node has an *implicit* one it fails silently. It would have been pinch-eligible (`armPinch` filters `#scroller` minus `#cursorStrip` and the grips), invisible to `camBusy()`, unseen by `armZoomTap`, and sized without the inverse-zoom divisor — four inherited faults, three of them re-runs of bugs this file has already paid for. The chips sit in a 16px band at the top of the rail, which grows 20px → 36px under `body.metered` **and only there**, so no shipped level's strip changes height. One delegated pointer state machine owns both: **the mode is decided once at pointerdown and held for the gesture**, because deciding per-move is how one drag becomes two half-gestures.

**THE LOOP RANGE NEEDED BOTH ENDS, and a one-sided test looked sufficient right up until it was written down.** `loopEnd` joins `loopStart`; the wrap became `bookCol < loopA() || bookCol >= loopB()`; and **an active range overrides the cursor pin in `start()`**, because otherwise pinning column 2 and selecting the bar at [8,16) plays fourteen columns rather than the bar — `start()` seeds `step` from the pin and `Transport.begin()` books from it. Measured on the device-equivalent path: bar 2 selected loops 8..15 forever; **with the cursor pinned at 2 it still loops 8..15**; released, it returns to 0..15. Unmetered, `loopA()`/`loopB()` reduce to `0`/`COLS`, so the surviving test is byte-identical to the `bookCol>=COLS` it replaced — confirmed by re-capturing goldens F/G/H content-identical. **A vine crossing `loopEnd` deliberately rings on** into the repeat: §6 says each instrument realises a duration honestly, and truncating would need a note-off the engine does not have.

**§5'S FOUR-COLUMN BEAT IS NOW ANSWERED FOR THE STUDIO ONLY, BY THE OWNER (2026-08-28): beat marks follow the TRUE PULSE, every 2 columns in 4/4.** `stepDur()` is `60000/tempo/2`, so at 108 BPM a column is 277.78 ms against a quarter's 555.56 — the tempo box has always treated a column as an eighth, and the drawing now agrees with it. **This forced a finding neither the design nor its review had: the Studio opens with drums ON, and `buildDrums` hardcoded `c%4===0` on every pad**, so melody beats every 2 columns beside pad tint every 4 would have put both conventions on one screen — the exact fault that killed round 1 of the decision itself. `beatTintAt(c)` makes the pads follow the meter when there is one and stay *byte-identically* `c%4===0` when there is not. It is the only line in this slice that shipped levels execute, and a test asserts the unmetered identity over 32 columns. `setBeatGuide`, `swingTicks`, `levelSwing` and all nine pieces of shipped copy are untouched: **for levels, §5 remains open.**

**TWO BUGS FOUND BY MEASURING, NOT BY READING.** `inChipBand` divided the pointer offset by `zoomOf()` while the band is sized `calc(16px / var(--fz))` *inside* a zoomed container — i.e. 16 **visual** px at every stop — so it compared a field-px offset against a visual-px height and, at zoom 0.6, **dropped the band's bottom 40% through to the cursor rail**. It belongs with the marquee's tap test and the pull's arming threshold as a deliberate viewport-px quantity. And **`resetTransient` cleared `doc.meterMap` but nothing redrew**: entering `stepping-stones` straight from a 4/4 Studio left the barlines, the chips, the 36px rail and the metered pad tint on screen while the model reported unmetered. The review had said resetTransient could not carry the quarantine alone and it was right — it now clears *and* redraws, verified across Studio → level → another level → Studio with a live loop range to strand.

**ALSO AS BUILT:** meter joins `snapState`, so one meter change is one undo step and redo restores the picture *and* the controls (`syncMeterUI()` is the single sync point, called from `setMeter`, `restoreSnapshot`, `applySong` and `resetTransient`) — **`applySong` must actively CLEAR on absence**, since meter is the first field that is legitimately missing and the conditional pattern tempo and groove use would have leaked a stale one. `＋/－ patch` moves by a bar when metered and by today's 16 otherwise, and metered removal is **all-or-nothing**: an 18-column waltz minus a 6-column bar would have clamped to 16 and taken only two, leaving a partial bar. The 16-column floor stays, but not for the reason its old comment gave — **`COLS` is assigned in five places and nothing ever grows it back**, so a Studio waltz trimmed to 6 columns would render every level entered afterwards at 6. 🎸 Jam is disabled for 3/4 and 6/8 (owner's call over my objection that an honest status line would do — it would not: Jam and Groove both overwrite the status). And a `songLoadToken` stops an in-flight `#song=` cloud fetch landing in a level the player walked into mid-request — a pre-existing race this slice would have taught to carry visible bars.

**✅ BUILT 2026-08-29 — THE DANCE GROOVES, in two PRs (a behaviour-preserving seam, then the content).** `💃 Waltz` and `🍀 Jig` are APPENDED to `GROOVES` and tagged `meter:["3/4"]` / `["6/8"]` — appended because `grooveIdx` is song state (`time.groove`, `snapState`, packed slot 4) and index 2 must stay Doo-wop forever, the same discipline slot 8 follows. Each declares `cycle:24` (four six-column bars) and `bar:6`; the untagged five keep the 16-column cycle that divides a 4/4 bar and a 2/4 bar exactly, which is why they could never play a waltz and why Jam was dark for two days. **The two dances fill the SAME bar and share nothing inside it** — waltz `bass·kick / — / chord·hat / — / chord·hat / —` against jig `chord·bass·kick·hat / hat / hat / chord·bass·kick·hat / hat / hat`, measured through the real audio helpers — which is §17's two-facts claim finally audible rather than merely drawn. A waltz has **no snare anywhere**, and a comp is not a bed: the stab holds 2 columns against the jig pulse's 3 and the shipped grooves' 4.

**THE BAND FOLLOWS THE BARS.** `jamStep` measures from `originTick`, so a pick-up shifts the band exactly as it shifts the barlines — verified with the waltz's OOM landing on the drawn barline at pick-ups 0, 1 and 2. Unmetered, and for any meter without a pick-up, the offset is zero and the expression is the one that shipped.

**A DESIGN REVIEW RETURNED REPLACE, AND ITS TWO CRITICAL FINDINGS ARE WORTH KEEPING.** First: the proposed generalisation `cyc = bar * prog` is **64** for the shipped grooves, not 16 — wrong by a factor of four, putting the wrong chord under nearly every column, and the design asserted in its own comment that it was identical. Second, and worse: **`D_jam` was offered as the proof, and `D_jam` cannot see the band.** Its capture wrapper records only THAT `jamStep` fired, and a groove's `kick`/`snare`/`hat` go straight onto `jamBus` rather than through `DRUMS[i].play` — which is why every one of its steps reads `drums: []` while a kit is audibly playing. The broken cycle would have re-captured it byte-identically. **`groovePlan` is therefore a pure function and `tests/groove.test.mjs` keeps a verbatim copy of the shipped logic as its oracle**, 485 comparisons across all five grooves and steps −32..64, plus 240 more through the real audio path in a browser. The rejected derivation differs at 5 of 7 sampled steps, so the oracle fails exactly where the golden passed. **The general rule, which `meterLayout` taught first: when a golden cannot see a thing, make that thing a pure function and compare it — do not trust the golden harder.**

**THE PREREQUISITE THAT WASN'T.** The design argued ＋ patch had to change, since 16 mod 6 = 4 and adding 6 preserves the remainder, so whole waltz bars are unreachable. **The bar loop range already loops two whole waltz bars in the default 16-column field** — measured as columns 0–11 repeating, six kicks, zero snares. The button was left alone. Its completion formula was wrong anyway: completion is `(COLS − origin) mod barCols`, so with a pick-up of 1 the last bar needs 3 columns, not 2.

**THREE CONTAINMENT HOLES THE SAME REVIEW FOUND.** `resetTransient` cleared Jam and the meter but **never `grooveIdx`**, so a Studio waltz walked into a level where a scripted `runReveal({jam:true})` would have played it on a six-column band — `normalizeGroove()` now runs there, and only an incompatible groove moves, so a player's Ballad still follows them in. Filtering the groove list is a **migration, not a validation**: since the meter slice shipped, real 3/4 songs have been saving whichever old groove was selected, because `currentSong` always writes `grooveIdx` whether or not Jam could use it — so `groove:0 + meter:"3/4"` is normal saved state and migrates to the dance on load, without letting the fallback overwrite the tempo the song carries. And normalisation runs **inside `setMeter`'s transaction**, because `grooveIdx` is part of `snapState` and a fallback journalled outside it would let undo restore the old meter beside the new groove.

**KNOWN AND DELIBERATE:** the jig ships at 138 quarter-BPM (92 dotted quarters) — a lilt rather than a session-speed jig, which would need 180 against a slider that caps at 170. Raising that cap is genuinely free (the sample ceiling derives from the SLOWEST tempo, and `FAMOUS_TEMPO` tops out at 156) and was left as its own decision rather than smuggled in here.

**DEFERRED, each on §17's or the owner's say-so:** ~~dance grooves~~ · count-in and metronome (`pulse` is in the preset table waiting for them) · famous-entry meter, hand-entered from scores · levels, which get no meter and no stage flag · and any snap control, which is what keeps §17's destructive-snap trap disarmed.

**TWO PRE-EXISTING BUGS FOUND IN PASSING, both their own tasks, neither caused by this design:** `FAMOUS_TEMPO.taps = 40` against the tempo slider's `min="60"` silently clamps, so **Taps has never played at its declared tempo**; and `placeFamous` closes its `tx()` before `playFamous` sets the tempo, so the famous tempo was never in the transaction's "after" snapshot and **redo of a famous reveal replays the arrangement at the player's tempo rather than the tune's**.

**Open:** crack-tap behavior pre-unlock (strategy B's "breathe open" gesture is a natural candidate for the "not yet" moment) · velocity level names/count (4 vs 5) · section-level meter/tempo divergence timing · scroll range limits by ear · when "can't-sound-bad" defaults start feeling restrictive (watch playtests; the Composer switch is one answer, earned dissonance is the in-game one).
